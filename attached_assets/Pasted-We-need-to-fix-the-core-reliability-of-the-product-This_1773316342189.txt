CORE GOAL

--------------------------------------------------
REQUIRED BEHAVIOR
--------------------------------------------------

The system currently checks for new listings every 10 minutes.
That is fine.

But from now on, every fetch cycle must work like this:

1. Fetch latest listings
2. Normalize incoming data
3. Deduplicate listings globally
4. Evaluate which active user search profiles match each listing
5. Create or update a canonical user_match record
6. Only then trigger:
   - app visibility
   - email delivery
   - push delivery
7. All counters in the UI must be based on these canonical user_match records, not on raw fetched items or temporary arrays

Important:
The app must NOT show inflated totals based on all historical imported records unless they actually exist as user_matches for that user.

--------------------------------------------------
CONSISTENCY RULES
--------------------------------------------------

For a given user:

- Home screen counts
- match tab counts
- number of email notifications sent
- number of push notifications sent
- visible match items in app

must all be explainable from the same underlying user_match table / collection.

This means:

- If 8 new matches were actually delivered in email, there should be 8 corresponding user_match records marked email_sent = true
- If push was sent for 8, there should be 8 user_match records marked push_sent = true
- If 8 are visible in the app, those same 8 should exist as visible_in_app = true
- Counters must be based on actual state, not assumptions

Do NOT count:
- duplicate fetches of the same listing
- old listings re-imported again
- listings that do not qualify for the active profile
- listings that were never actually delivered or shown

--------------------------------------------------
DEDUPLICATION
--------------------------------------------------

Implement strong deduplication.

A listing must not produce duplicate user matches because:
- the scraper fetched it again
- the polling cycle ran again
- the same listing came from slightly different source payloads

Create a reliable deduplication strategy based on a stable listing identity.
Use a strong canonical key such as source + external listing id.
If needed, add fallback normalization using URL normalization / address / title fingerprint, but prefer stable source IDs first.

Also prevent duplicate user notifications:
- no duplicate email for same user_match
- no duplicate push for same user_match
unless there is an intentional resend mechanism

--------------------------------------------------
CORRECT MATCH ORDERING

The app value is that users see the newest relevant listings first.

Therefore:
- matches in the app must be ordered by actual listing freshness / detected time
- newest valid matches first
- not random
- not mixed with stale duplicates
- not sorted by accidental insert order if that is incorrect

Make sure the home screen preview, match list, and notification logic all use the same ordering logic.
