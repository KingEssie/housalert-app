We need to clean up the Search Buddy system now that the underlying bug has been fixed.

IMPORTANT:
- Do NOT use temporary workarounds anymore
- Remove old emergency restrictions that were added only because buddies were incorrectly being treated as main users
- Fully support buddy self-unsubscribe from email
- Keep the system safe: no removed/revoked buddy may ever receive future emails

==================================================
PART 1 — REMOVE TEMPORARY BLOCKED EMAIL WORKAROUNDS
==================================================

Audit the current Search Buddy implementation for any temporary email blocking logic.

We previously blocked 1 or more specific email addresses because Search Buddy emails were behaving incorrectly and those buddies were being treated like main users.

Now that the real Search Buddy logic is fixed, remove these temporary blocked-email workarounds.

This includes:
- hardcoded blocked email addresses
- denylist checks added only as a workaround
- special-case conditions preventing those addresses from being used as Search Buddy

IMPORTANT:
Only remove the workaround logic if the current Search Buddy send-time validation and ownership logic are already correct.
Do NOT reintroduce the original bug.

==================================================
PART 2 — BUDDY UNSUBSCRIBE MUST REMOVE THE BUDDY RELATION
==================================================

When a Search Buddy clicks "unsubscribe" in an email, this must do more than stop email delivery.

It must fully remove/deactivate the Search Buddy relationship.

Required behavior when buddy unsubscribes from email:
1. validate the unsubscribe token/link securely
2. find the active buddy relationship
3. mark the buddy as no longer active
4. store a clear status such as:
   - revoked_by_buddy
   OR
   - removed
5. set timestamp like revoked_at / removed_at
6. stop all future buddy emails immediately
7. remove the buddy from the main user's active Search Buddy UI
8. invalidate caches / stale state
9. ensure queued jobs can no longer send to that buddy

IMPORTANT:
A buddy unsubscribing from mail must functionally behave like:
"this buddy is no longer an active search buddy"

==================================================
PART 3 — SERVER-SIDE ELIGIBILITY MUST STILL HOLD
==================================================

Keep the existing strict eligibility logic.

A Search Buddy may receive emails ONLY if:
- buddy email exists and is valid
- buddy status is active
- owner user has active paid subscription OR active trial
- owner account is not suspended/disabled
- buddy has not been removed/revoked/unsubscribed
- send-time validation passes

If buddy status is revoked_by_buddy / removed / inactive:
- never send again

==================================================
PART 4 — MAIN USER UI SYNC
==================================================

If a buddy unsubscribes via email:
- the main user must no longer see that buddy as active
- the invite/search buddy screen should reflect that no active buddy exists
- the main user should be able to invite a new buddy again

If there is a status label/message system, optionally show:
"Je zoekbuddy heeft zich afgemeld voor meldingen"

But only if that fits the current UI cleanly.

==================================================
PART 5 — DATA MODEL
==================================================

Use a proper status-driven relationship model for Search Buddy.

Preferred statuses:
- pending
- active
- removed_by_owner
- revoked_by_buddy
- expired

If a simpler equivalent already exists, normalize it and use it consistently.
Do NOT rely only on a raw email field.
